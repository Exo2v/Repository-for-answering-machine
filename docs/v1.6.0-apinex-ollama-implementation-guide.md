# Screen Answer v1.6.0 Experimental — APInex + Ollama Implementation Guide

> This is a release-specific implementation reference, not the whole-project manual. For the standard app, Lasso variants, OCR, diagnostics, configuration, privacy, tests, release history, and current distribution status, see the [project-wide guide](project-guide.md). The later v1.7.0-experimental standard build adds `free/gpt-6-luna` as an optional APInex model; this guide's implementation details describe the v1.6.0 release snapshot. A subsequent current-branch change restores direct Google Gemini as a separate standard-app provider; it does not add Gemini to any Lasso build.

## 1. Executive summary

Screen Answer is a Windows notification-area application that captures the full virtual desktop only after a user-triggered action. It sends the in-memory image to the chosen vision solver, parses an explicit answer, and reports the answer position using the tray icon's color.

This release changes the standard Screen Answer provider list because the direct Google Gemini and Groq routes were not working for the user. The standard app now offers:

1. **APInex** — hosted vision API; default provider and default model alias `free/gemini-3.8-flash`.
2. **Ollama (local)** — local vision inference at `http://127.0.0.1:11434/api/chat`; default model `qwen3-vl:8b`; no API key.
3. **Mistral** — retained hosted option; provider-default behavior uses Mistral OCR followed by Mistral chat.
4. **OpenRouter** — retained hosted option; constrained to two explicit Gemma `:free` vision model IDs.

The direct Google/Gemini API and Groq provider implementations were removed from the standard app. **This does not mean every Google-family model ID was prohibited:** APInex's default catalog ID still contains `gemini`, and OpenRouter's two allowlisted IDs contain `google/gemma`. Those requests go through APInex or OpenRouter, not Google's direct API, and do not use a Google API key. If “remove Google” means banning those model families too, the current APInex/OpenRouter defaults need a different explicitly selected vision-model allowlist.

No APInex key, Ollama service, model weights, portable config, or `servomotor` file is included in the release. Standard screenshot consent starts off and must be explicitly saved before capture is allowed.

## 2. What this release is intended to solve

The requested test version has two different ways to answer an image question:

- **APInex tests a hosted route.** It offers an OpenAI-compatible chat-completions interface and advertises a free-category model allowance. The app sends the screenshot to APInex, which routes it to an upstream vision model. This tests whether a hosted API is reliable and useful for the intended workload.
- **Ollama tests local inference.** The app sends the screenshot to a local Ollama server on the same computer. This avoids sending the screenshot to a cloud model API through this app and avoids an API key, but it requires the user to install Ollama, download a large model, and have enough local hardware for acceptable speed and quality.

The test build does not promise that APInex is free for every account or that the local model will run well on every computer. The next decision should be based on measured answer quality, latency, quota use, cost behavior, and data-handling requirements—not model names alone.

## 3. Scope and boundaries

### Included in the standard Screen Answer app

- Provider choices: APInex, Ollama, Mistral, OpenRouter.
- APInex and Ollama screenshot request implementations and response parsing.
- Per-provider key requirements, model validation, upload-consent messages, and error feedback.
- Optional Pix2Text local OCR. It extracts text/formulas; it does not solve the question.
- Optional `screen_answer_config.json` sidecar for standard-app settings.
- Windows builds for `ScreenAnswer.exe` and `ScreenAnswer-Diagnostic.exe`.

### Removed from the standard app

- Direct Google Gemini provider and `GEMINI_API_KEY` support.
- Direct Groq provider and `GROQ_API_KEY` support.
- The dedicated `ScreenAnswer-Groq.exe` release asset/build step.
- Migration of an old unscoped/Google key into APInex. An old Google key is not an APInex key and must not be reused as one.

### Explicitly unchanged / out of scope

- **Dedicated LassoV2 and LassV27 builds remain OpenRouter-only.** This release does not add APInex or Ollama to those builds.
- The Lasso Settings GUI remains on-demand, has no model field, and keeps model selection in each Lasso executable's per-user config. Saving Lasso Settings closes the window.
- Lasso config paths remain `%APPDATA%\LassoV2\config.json` and `%APPDATA%\LassV27\config.json`; Lasso1/LassV7 paths and cleanup behavior are unchanged.
- No change to the multiple-choice task contract: the app expects one single-answer question with four choices. Free-response, multi-select, and arbitrary problem formats are not added here.
- No live web search, browsing, tool calls, or external search plugins are enabled in the solver request.
- No automatic fallback from APInex to Ollama, Mistral, or OpenRouter (or between paid/free model families) is performed. A provider failure should result in a neutral/unknown result, not a silent reroute.

## 4. High-level user flow

1. Launch the standard EXE. The app starts with a visible tray icon and settings available on demand.
2. Choose a provider in Settings. APInex is the standard default. Ollama can be selected without entering a key.
3. Select the OCR backend. **Provider default** means APInex, Ollama, and OpenRouter use image vision directly; Mistral uses its hosted OCR-first path. **Pix2Text (local, experimental)** runs OCR locally, then passes the original image plus OCR text to the selected solver.
4. Enter a key for a hosted provider, if needed. API keys are not embedded in the executable. Ollama has no API-key field.
5. Read and check the provider-specific screenshot/data-path notice, select its consent box, and click **Save settings**. In the standard app, consent is session-only: it starts unchecked after each launch and is not persisted in the sidecar.
6. Press **Ctrl+Alt+S** or select the capture action. The app captures the whole virtual desktop/all monitors, encodes a PNG in memory, and starts a background request. It does not save the screenshot to disk.
7. The solver is asked for an explicit final line `ANSWER: n`. The result position is mapped to a tray color. An unreadable, ambiguous, or failed response remains neutral/grey; the app does not guess from an unlabeled number.

The tray maps positions as follows:

| Answer position | Tray color |
| ---: | --- |
| 1 | Red |
| 2 | Yellow |
| 3 | Green |
| 4 | Blue |
| No reliable answer / request failure / ready | Grey/neutral |

A successful result remains at full color for about 10 seconds, then fades to grey over about 1.5 seconds. Standard builds can also show app status/notifications; LassV7 retains its separate rule that tray color is the only runtime feedback, with no app-generated balloons or hover tooltips.

## 5. Data flow and privacy model

### Capture and image handling

- Capture is user-triggered; the app does not continuously record the desktop or install a startup task.
- The capture includes the full virtual desktop/all connected monitors. It can therefore contain unrelated windows, notifications, personal data, or credentials visible on screen. Close or hide sensitive material before consenting.
- The image is encoded as PNG and held in process memory for the request. It is not written as a screenshot file. The worker drops its reference when the request finishes.
- Capture limits are set in the app (`MAX_SCREEN_PIXELS = 24,000,000`; `MAX_PNG_BYTES = 12 MiB`). These reduce pathological payloads; they do not crop the desktop or make its content non-sensitive.

### Where the screenshot goes

| Selected provider | Destination from the app | Key? | Data-path summary |
| --- | --- | ---: | --- |
| APInex | `https://api.apinex.bond/v1/chat/completions` | Yes | Full PNG is sent to APInex; APInex may pass it to its selected upstream vision model. Review both the intermediary and applicable upstream terms. |
| Ollama | `http://127.0.0.1:11434/api/chat` | No | Full PNG is sent to the local loopback Ollama service on this computer. This app does not send it to a cloud model API in this mode. Do not substitute an untrusted remote Ollama endpoint. |
| Mistral | `https://api.mistral.ai/v1/ocr`, then chat endpoint by default | Yes | Provider-default OCR sends the image to Mistral OCR and then sends the original image plus OCR text to Mistral chat. Local Pix2Text skips the separate Mistral OCR call. |
| OpenRouter | `https://openrouter.ai/api/v1/chat/completions` | Yes | The image is sent through OpenRouter to its selected model host. Host-specific data terms apply. |

The consent checkbox is deliberately provider-specific. Switching provider or OCR mode clears consent so the user must read and acknowledge the new data path. For the standard app, consent is not stored: it is off at every new launch, including when a provider key/model sidecar already exists. For dedicated Lasso builds, the separate existing config behavior stores `allow_screenshot_uploads`; this release did not alter it.

### Keys and configuration

Supported environment variables for hosted standard-app providers are:

- `APINEX_API_KEY`
- `MISTRAL_API_KEY`
- `OPENROUTER_API_KEY`

Ollama has no key and no `OLLAMA_API_KEY`. In standard Screen Answer, an environment key may prefill the masked Settings field. A key entered by the user is kept in memory for the current run unless the optional portable-config checkbox is selected. When selected, settings are saved in plaintext to `screen_answer_config.json` beside the Python source or executable. Treat that file as secret, do not email/share it, and do not include it with a public release. The release contains only the two EXEs; no sidecar is bundled.

The standard app's first-run key fields are blank unless the user has configured an environment variable. Lasso builds use their own `%APPDATA%` config paths and deliberately ignore environment keys.

### Diagnostics

The standard diagnostic executable opens a live diagnostics window at startup; the ordinary ScreenAnswer executable does not. Logs can include timing, model names, HTTP statuses, rate-limit headers, token counts when returned, OCR text, final model output, and provider-supplied error details. They omit API keys and screenshot pixels, but screen-derived text can still be sensitive. Review a log before copying, saving, or sharing it. Lasso diagnostic pages remain on-demand.

## 6. Provider implementation details

### 6.1 APInex

**Endpoint:** `https://api.apinex.bond/v1/chat/completions`<br>
**Authentication:** `Authorization: Bearer <user's APInex key>`<br>
**Default model:** `free/gemini-3.8-flash`<br>
**Second permitted ID:** `free/gemini-3.1-pro`<br>
**Other model IDs:** rejected before network access.

The APInex code builds one OpenAI-compatible chat request. It sends the system instruction and user prompt as text, plus a PNG data URL in an `image_url` content part. The request sets `temperature: 0`, a 2,048-token output ceiling, and `reasoning_effort: "medium"`. There is no `tools` or `plugins` field. When Pix2Text is enabled, a bounded OCR transcript is included as untrusted text context; the original image remains attached as the source of truth.

Illustrative, redacted request shape:

```json
{
  "model": "free/gemini-3.8-flash",
  "messages": [
    {"role": "system", "content": "<solver instructions; no live web search or tools>"},
    {
      "role": "user",
      "content": [
        {"type": "text", "text": "<question prompt and optional OCR context>"},
        {"type": "image_url", "image_url": {"url": "data:image/png;base64,<in-memory PNG>"}}
      ]
    }
  ],
  "temperature": 0,
  "max_tokens": 2048,
  "reasoning_effort": "medium"
}
```

Response handling reads the first chat-completion choice's user-facing `message.content`. If the provider returns reasoning separately (for example `reasoning_content`), that separate field is not shown, parsed, or logged. When available, response metadata and token-usage counts are logged in Diagnostic mode; final visible response text may also appear in the diagnostic window.

Transient handling is bounded to three attempts. HTTP 429 uses `Retry-After` when usable or bounded backoff; temporary HTTP 5xx statuses are retried. 401/403 gives a key/permission message, 402 points to account balance/free allowance, 413 indicates the screenshot was too large, 400 indicates a model/image-format rejection, and 404 indicates a model/route issue. There is no paid-model fallback. A free-category name is not itself a billing guarantee: check the account's current quota and actual billing behavior.

**Unresolved APInex research risk:** public APInex materials advertise a daily free-category token allowance and a 5-requests/minute free-tier limit. The public pricing/model pages have also shown nonzero retail pricing beside some `free/...` IDs. It is not verified here how an account is charged after its daily allowance or how image tokens are weighted. No key/account was used to resolve that mismatch. Test with a synthetic image and verify the account counter and billing before sustained use.

References: [APInex auth](https://apinex.bond/developers/auth), [model list](https://apinex.bond/developers/models), [chat API](https://apinex.bond/developers/models/chat), [pricing](https://apinex.bond/pricing), and [error/rate-limit docs](https://apinex.bond/developers/errors).

### 6.2 Ollama (local)

**Endpoint:** `http://127.0.0.1:11434/api/chat`<br>
**Authentication:** none<br>
**Default model:** `qwen3-vl:8b`<br>
**Timeout:** 300 seconds.

The app calls Ollama's native local chat API and sends the PNG as base64 in the user message's `images` array. It sets `stream: false`, `temperature: 0`, and `num_predict: 2048`. It has no Authorization header, cloud fallback, tools, or remote-host setting. Selecting Ollama therefore requires an Ollama server listening on loopback on the same machine.

Illustrative request shape:

```json
{
  "model": "qwen3-vl:8b",
  "messages": [
    {"role": "system", "content": "<solver instructions; no live web search or tools>"},
    {
      "role": "user",
      "content": "<question prompt and optional OCR context>",
      "images": ["<base64 PNG bytes, without a data: prefix>"]
    }
  ],
  "stream": false,
  "options": {"temperature": 0, "num_predict": 2048}
}
```

Install Ollama separately and download the model before use:

```powershell
ollama pull qwen3-vl:8b
```

The documented Qwen3-VL package requires Ollama 0.12.7 or newer and is a multi-gigabyte download (about 6 GB in the model listing reviewed for this release). Local RAM/VRAM needs and latency depend on the computer and installed quantization. The EXE does not bundle Ollama or model weights. A missing-model 404 explains how to pull the model; a connection error asks the user to start Ollama. A configured model name is syntax-validated, but the app cannot prove that an arbitrary custom Ollama model is installed or supports vision until the request is attempted.

Ollama returns user-facing text in `message.content`; separate `message.thinking` is not parsed or displayed. Diagnostics can include token/timing metadata and final response text. The request implementation has a 300-second timeout and gives clear common error messages; unlike the hosted retry handlers, it does not automatically retry an Ollama request.

References: [Ollama chat API](https://docs.ollama.com/api/chat), [vision guide](https://docs.ollama.com/capabilities/vision), and [Qwen3-VL model listing](https://ollama.com/library/qwen3-vl).

### 6.3 Mistral and OpenRouter retained in the standard app

**Mistral** remains an editable standard-app option. Its model defaults to `mistral-medium-latest`; legacy `ministral-14b-2512` config values are migrated to that default. With Provider default OCR, the app sends the image to Mistral OCR and then sends the image plus OCR transcript to Mistral chat. If Mistral OCR fails, chat can continue with the original image. Pix2Text can instead OCR locally, skipping Mistral's separate OCR request.

**OpenRouter** remains an editable standard-app option, restricted to:

- `google/gemma-4-31b-it:free` (default)
- `google/gemma-4-26b-a4b-it:free`

These are exact allowlisted `:free` IDs; paid IDs and online/search variants are rejected. No paid fallback is made. The OpenRouter endpoint is `https://openrouter.ai/api/v1/chat/completions`, and `OPENROUTER_API_KEY` is supported. OpenRouter still routes the screenshot to its model host, so that host's data terms apply.

## 7. Prompt, OCR, and answer parsing

The shared solver instruction treats the screenshot and OCR transcript as untrusted question data, tells the model not to follow instructions found inside them, asks it to solve exactly one single-answer four-choice problem, and requests a concise, checkable solution. It asks the solver to transcribe the question, identify relevant details, work and check the calculation, map letters/numbers to positions, and finish with `ANSWER: 1`, `ANSWER: 2`, `ANSWER: 3`, `ANSWER: 4`, or `ANSWER: 0` when it cannot reliably answer.

The parser favors an explicit labeled answer line. It maps A/1 to position 1, B/2 to 2, C/3 to 3, and D/4 to 4. A number elsewhere in the explanation should not become the tray answer. If there is no unambiguous valid answer line, the app returns neutral/grey rather than guessing. This release does not add free-response or multi-select parsing.

Pix2Text is optional and runs on-device. It can help with small text and formula transcription, but it can be wrong; the prompt tells the model to verify OCR against the original image. The OCR string is capped at 48,000 characters. With APInex, Ollama, or OpenRouter, OCR is supplemental context and the image is still sent through the selected provider. With Mistral, local Pix2Text replaces the separate OCR API call but the screenshot and transcript are still sent to Mistral chat. Pix2Text is not an offline solver.

## 8. Configuration and migration behavior

### Standard app

- Default provider: `apinex`.
- Default APInex model: `free/gemini-3.8-flash`.
- Default Ollama model: `qwen3-vl:8b`.
- Default Mistral model: `mistral-medium-latest`.
- Default OpenRouter model: `google/gemma-4-31b-it:free`.
- Hosted keys are looked up in environment variables first and then in supported sidecar fields. Ollama always resolves to an empty key.
- If portable saving is disabled, standard provider/model settings stay in memory for that run. If enabled, settings are written as plaintext beside the source or EXE to `screen_answer_config.json`.
- Standard screenshot consent is not in the config file and is re-acknowledged on each run.

Config loading filters unknown/retired provider keys and models. Old Gemini/Groq values are not offered as providers. A legacy flat `api_key` with no recognized provider is not moved to APInex, and retired values are removed from the sidecar when it can be rewritten. The app validates APInex/OpenRouter models against exact allowlists, validates Ollama model-name characters, and supplies safe defaults for invalid models. Ollama keys are never saved. The sidecar is excluded from Git by `.gitignore` and is not part of GitHub release assets.

### Dedicated Lasso builds

Lasso executables are deliberately isolated from the standard provider migration. LassoV2/LassV27 remain OpenRouter-only, use their own per-user config folders, read the API key from the matching config, and expose no model selector in Settings. Their current release behavior, config paths, screenshot consent, diagnostics, and cleanup rules are described in the main [README](../README.md); this v1.6 standard-provider change does not alter them.

## 9. Diagnostics, errors, and safe failure

The diagnostic EXE opens a live log at startup. The standard app can also run from source with `python answer_tray.py --diagnostics`. The log can show startup/config state, capture dimensions and duration, provider/HTTP attempt, status, retry delay, selected model, available rate-limit headers, usage counts, OCR Markdown, final user-facing model text, parsing outcome, and error details.

The log is not a screenshot archive: PNG pixels and API-key values are omitted/redacted. However, OCR text and final model output can reproduce sensitive content visible on the screen. Do not paste a log into an issue or public chat without reviewing and sanitizing it. A key error, no response, unreadable image, invalid model, missing Ollama service, or ambiguous answer should not turn into a guessed color answer.

The implementation caps provider response bodies at 2 MiB and bounds transient hosted retries to three attempts. APInex and other hosted request handlers omit screenshot/body content from diagnostics. Ollama uses loopback and does not have an API key. There is no cross-provider failover.

The public prerelease is [`v1.6.0-experimental`](https://github.com/Exo2v/indigo-otter-731/releases/tag/v1.6.0-experimental). Its assets are:

- [`ScreenAnswer.exe`](https://github.com/Exo2v/indigo-otter-731/releases/download/v1.6.0-experimental/ScreenAnswer.exe)

It runs the tests, builds one-file/windowed executables, runs the packaged smoke checks, and attaches only the two EXEs above. It does not attach `screen_answer_config.json`, API keys, model weights, `servomotor`, or source-side user credentials. To reproduce a standard build on a suitable Windows machine:

```powershell
python -m pip install pyinstaller==5.13.2
pyinstaller --noconfirm --onefile --windowed --name ScreenAnswer answer_tray.py
pyinstaller --noconfirm --onefile --windowed --name ScreenAnswer-Diagnostic answer_tray.py
```

For the best chance of Windows 7 compatibility, use 32-bit Python 3.8.10 as the CI workflow does. Ollama itself is a separate install and may not be supported on older Windows versions; the standard Screen Answer EXE does not bundle or guarantee the Ollama server.

## 12. Recommended hands-on validation checklist

Use a synthetic/non-sensitive screenshot first. Do not begin with a real personal desktop capture.

### APInex pilot

- [ ] Review APInex's current privacy, terms, pricing, and authentication documentation.
- [ ] Create a key directly in the user's own APInex account; never paste it into source control, support tickets, or this document.
- [ ] Run ScreenAnswer, select APInex, confirm the exact allowed model, enter the key, read the upload notice, and save consent.
- [ ] Use a synthetic known-answer image; confirm a response, tray position, and response/token metadata in diagnostics.
- [ ] Check the account's free quota and billing state before and after; do not infer “no charge” solely from a model ID containing `free`.
- [ ] Repeat several known-answer cases, record accuracy/latency/token usage, and stop if billing or quota behavior is unclear.

### Ollama pilot

- [ ] Install Ollama 0.12.7 or later and run `ollama pull qwen3-vl:8b`.
- [ ] Confirm the service is local and listening at `127.0.0.1:11434`.
- [ ] Select **Ollama (local)** in Screen Answer. Verify the API-key field is disabled/blank and the local data-path notice is understood.
- [ ] Test a synthetic image and verify the model returns an explicit `ANSWER: n` line and the expected tray color.
- [ ] Measure startup/load time, inference latency, memory pressure, and accuracy on the actual target computer.

### Compare before relying on either backend

- [ ] Use the same small, labeled test set for both paths: arithmetic, algebra, units/signs, diagrams, and irrelevant visual details.
- [ ] Record correct/incorrect, neutral result, latency, model/version, API usage or local resource use, and error behavior.
- [ ] Only expand to real captures after data handling is acceptable and the test set shows the needed answer quality.
- [ ] Keep the desktop free of sensitive data; each capture sends all monitors to the selected solver unless Ollama is selected and the local server is trusted.

## 13. Known limitations and open risks

1. **APInex pricing/allowance is not resolved.** Public pages have presented free-category daily allowance information alongside nonzero retail pricing. A paid model is not selected as fallback, but the code cannot guarantee APInex's account-level billing behavior. Verify balance, quota, and exhaustion semantics in the user's account.
2. **No live API inference was performed for this release.** Unit tests mock network responses. APInex base64 compatibility, real quota accounting, upstream model quality, and Ollama local execution still need a user pilot.
3. **Ollama is local but resource-intensive.** The model requires a multi-gigabyte download and may be slow or fail on a low-memory/CPU-only computer. Model version, quantization, and hardware affect quality and latency.
4. **The screenshot is the entire desktop.** Users must consider all visible screens/windows. A local OCR option does not anonymize the screenshot or make a hosted solver private.
5. **The answer format is narrow.** One four-choice question is expected. Multiple questions, multi-select, free-response, and ambiguous diagrams can result in a neutral answer.
6. **APInex/OpenRouter model names still mention Google families.** The direct Google provider is removed, but APInex's default alias and OpenRouter Gemma IDs are intentionally retained behind their respective intermediaries. Change only if the user means all Google-family models are prohibited.
7. **Free model availability changes.** Models, quotas, privacy terms, API schemas, and provider behavior can change. The app validates configured IDs, but cannot guarantee external service uptime or exact free status.
8. **Diagnostics can expose screen-derived text.** Logs exclude image pixels and keys but can contain OCR and final responses. Review them before sharing.
